# backend · 3D 搜索轻后端（Day 7 / 方案乙）

把「物资数据」包装成一个 HTTP 接口，供 `3d-warehouse` 前端调用。

**一句话**：前端不再自己读文件，改成问后端要数据 —— 这样凭据留在服务端，业务规则留在服务端，前端换数据源也不用改。

---

## 1. 为什么要这一层

对齐 `TECH_DESIGN.md` 第 3 节选定的**方案 X**，三条理由：

| 理由 | 说明 |
| --- | --- |
| 凭据不进浏览器 | 访问腾讯文档的密钥只留在服务端。本仓库是**公开仓库**，凭据进前端等于泄露。 |
| 业务规则前移 | 字段翻译、层级推导、脏数据过滤都在这里做，前端只管显示。 |
| 前端可替换 | 以后换数据源（快照 / 数据库 / 腾讯文档），前端一行都不用改。 |

---

## 2. 两种运行模式

对外接口完全一致，前端感知不到差别 —— 这正是「适配层」的价值。

| 模式 | 需要凭据 | 数据来自 | 用途 |
| --- | --- | --- | --- |
| `seed`（默认） | ❌ 不需要 | `data/seed.json` 快照 | 开发、演示、离线跑 |
| `tencent` | ✅ 需要环境变量 | 腾讯文档智能表 | 真实数据 |

### seed 模式（推荐先跑这个）

```bash
python backend/server.py
# 输出：3D 搜索后端已启动  http://127.0.0.1:8011
```

### tencent 模式

需要两个环境变量（`tdoc_bridge` 会检查，缺失即报错，避免误连）：

```bash
export WORKBUDDY_TDOC_PLUGIN="<本机 tencent-docs skill 目录>"
export TDOC_FILE_ID="<目标文档 file_id>"
export TDOC_SHEET_MAT="<物资档案 sheet_id>"

python backend/server.py --source tencent
```

> ⚠️ **红线**：`TDOC_FILE_ID` 只允许指向**测试副本**。正式文档严禁写入。
> 本仓库所有文档都不记录真实 ID，一律从环境变量注入。

## 3. 接口

| 方法 | 路径 | 返回 |
| --- | --- | --- |
| GET | `/api/health` | `{ ok, source, items }` —— 健康检查 |
| GET | `/api/items` | `{ source, label, items: [...] }` —— 全部物资 |

`items` 元素结构（前端唯一消费的格式）：

```json
{
  "materialId": "FZ-SP-00001",
  "materialName": "不锈钢餐盘",
  "campus": "福州校区",
  "zone": "A",
  "row": 1,
  "level": 2,
  "boxId": "A-01-02",
  "position": { "x": -22, "y": 3.4, "z": 0 },
  "dataStatus": "演示数据"
}
```

## 4. 前端怎么切过来

改一个常量即可（`src/config.js`）：

```js
export const DATA_SOURCE = 'api';   // 改成 'api'，其余不动
```

- `DATA_SOURCE = 'demo'` → 前端直接读本地 `data/demo-data.json`（离线，默认）
- `DATA_SOURCE = 'api'` → 走本后端
- **降级保护**：`api` 模式下如果后端没启动，前端会自动退回本地演示数据并在控制台告警，页面不会白屏。

后端地址默认 `http://127.0.0.1:8011`，可在页面里用 `window.__API_BASE` 覆盖。

## 5. ⚠️ 已发现的数据缺口（重要，需业务确认）

对着物资档案表的字段定义清单（旧项目 `docs/schema/raw/` 下的字段导出文件）逐项核对后确认：

**档案表里有定位字段：区域、箱子编号、排、校区 —— 但【没有"层"】。**

3D 场景要摆箱子，必须知道「第几层」。当前的处理方式是**从【箱子编号】反推**：

```
箱子编号 A-01-02
          │  │  └── 第 3 段 = 2 层
          │  └───── 第 2 段 = 1 排
          └──────── 第 1 段 = A 区
```

**这个反推成立的前提**是现场确实按 `区域-排-层` 编号。三种可能：

| 情况 | 表现 | 应对 |
| --- | --- | --- |
| 编号规范 | `A-01-02` 这种格式统一 | 反推可用，无需改动 |
| 编号不规范 | 出现 `A-1-2`、`A0102`、空值等 | 反推出错或跳过该条 |
| 现场按"箱"不按"层"管理 | 箱子编号与层无对应关系 | **必须补列或改用人工盘点数据** |

代码里的防御措施（`server.py` 的 `normalize()`）：

- 排号优先取【排】字段，取不到才从箱子编号第 2 段兜底
- 层号推不出时**默认第 1 层**，不报错
- 超出货架范围（A/B/C 区各 3 排 3 层）的记录会打 `[skip]` 日志并**跳过**，避免前端渲染到画布外

**建议**：接入真实数据前，先拉 10 条样本对照现场核对编号规则。若规则不成立，需要在智能表补一列「层」，或改由人工盘点表提供。

## 6. 已知限制

| 限制 | 说明 |
| --- | --- |
| 只读 | 本后端只提供查询，不含借用/归还/领用（那些在 `prototype_server.py`，本次未并入） |
| 无缓存 | 每次请求都重新读数据源；真实模式下数据量大时应加缓存 |
| 无鉴权 | 仅监听 `127.0.0.1`，本机使用；公网部署必须加鉴权 |
| 坐标公式双份 | `server.py` 与前端 `src/layout.js` 各有一份坐标公式，**改动必须同步**（见下） |

### 关于「坐标公式双份」

`position_for()`（Python）和 `positionFor()`（JS）实现同一套坐标换算：

```
x = 区域中心（A=-22, B=0, C=22）
y = (层 - 1) × 2.4 + 1.0
z = (排 - 1) × 5.0
```

两种语言无法共享代码，只能各写一份。**风险**：改了一边忘了另一边 → 箱子错位。
**缓解**：已写进注释互相指向；`verify/verify-api.mjs` 会校验后端返回值与前端渲染结果一致。
若后续要彻底消除，可让后端只返回 `zone/row/level`，把坐标计算完全交给前端 `layout.js`。
